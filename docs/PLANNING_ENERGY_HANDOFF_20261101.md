## Implemented source behavior

- **Device priority flag:** existing per-device manual hold is the priority flag. App exposes MANUAL HOLD or NO MANUAL HOLD, last applied output source and last schedule outcome. Existing manual and confirmed Vosk paths remain separate and unchanged in recognition semantics. No arbitrary CPU-priority setting was added.
- **Resolution:** SafetyKernel constraints first. Manual/confirmed voice commands cancel a pending schedule for that device when applied. A rejected manual request does not change the mode or cancel the schedule. Explicitly arming a schedule releases that device's manual hold; this is explained in an authorization dialog. Queued explicit commands run before schedule policy in each bounded controller cycle. Existing OFF timers and user-authorized energy caps may turn OFF manual ON and are disclosed as exceptions to the hold.
- **One-shot controller schedules:** one pending ON or OFF per physical device. App accepts the next local HH:mm; converts it at authorization to a relative delay, 1 second through 24 hours. Setting another replaces the device's pending rule; Cancel removes it. Countdown starts when A accepts the command, so the chosen wall time has transport/processing delay. This is not a synchronized RTC/calendar service. No daily/weekly recurrence or multi-entry calendar queue is claimed.
- **Autonomy:** A owns the countdown after acceptance; the phone can disconnect. An action is attempted once, through SafetyKernel. Dwell/policy denial is shown as Blocked and is not retried. Actions over one second late are consumed as Blocked. A subsequent reconnect does not dispatch old work. Reboot clears schedules and energy caps; outputs still start OFF. The app does not silently re-arm anything. Runtime plans are deliberately volatile; the existing policy/manual configuration persistence remains separate.
- **Conservation:** per-device optional maximum continuous ON cap, app range 1–240 minutes; API supports 3 seconds–4 hours. Enabling an already-overdue cap can request OFF at the next control tick, subject to dwell. Disabling it never turns ON. Cap does not reset the current ON duration or bypass four-hour SafetyKernel cutoff. Existing OFF timers, minimum dwell and maximum-run guard remain. App shows current cap, software-reported ON counters, last OFF source, assumed light/fan wattage and an estimated Wh total since controller boot. Watts are optional local display preferences. No measured appliance energy, avoided kWh, cost savings, percentage saving or battery-life improvement is claimed. There is no electrical feedback or baseline power trace.
- **Speech report:** an expandable report in Rooms/Overview includes MN6 synthetic/phone failures, the 25 October MN6 and MN7 reference outcomes, successful recorded Vosk command/ACK/readback trials, processing location, fixed gate/model details and negative-test limitations. MN6 short reference ENABLE was 0.73673 in the authoritative report; MN7 ENABLE was 0.85891. Engine scores are not cross-engine accuracy percentages. Reports are historical evidence, not new microphone tests.
- **Deferred:** new light sensor, sensor-driven light/fan rules and temperature hysteresis. No PIR restoration. DHT11 remains monitoring only. Existing active-HIGH GPIO4/GPIO5 and DHT11 GPIO7 definitions are unchanged.

## Protocol and review details

- Control envelope/ACK sizes and authentication remain unchanged. New op7 Schedule: device0 light/1 fan; action0 OFF,1 ON,2 cancel; value delay_ms (cancel requires zero). New op8 Energy: action0; value cap_ms (zero disables).
- Authenticated `/api/control` uses `boot <expected_boot> <op> <device> <action> <value>` for new features. Parser rejects missing/zero/overflowed boot bindings. B binds dispatch to that current boot. Existing legacy four-field commands retain their behavior.
- Radio room schema6 is 80 bytes, adding two 12-byte feature entries; 80+16 auth bytes fits the 220-byte payload limit. Updated B also decodes legacy 44-byte schema3 and 56-byte schemas4/5. Old B cannot decode schema6: deploy updated B before updated A after local build checks. Do not roll A forward by itself.
- HTTP temperature telemetry stays schema4 and manual policy stays version2. `features_version:1` advertises the schedule/cap fields. Old firmware lacks the capability and the app refuses feature dispatch. Enabled outputs also require the already approved LED profile; generic enabled output profiles do not unlock these controls.
- App configuration submissions use one existing transaction owner, explicit authorization, boot binding, matching applied ACK and advancing fresh same-boot configuration readback. HTTP202 is pending, not success. Timeouts/disconnects do not retry. Configuration ACKs do not unlock the voice manual-proof gate. For a very short schedule, reported configuration can include its already executed/blocked result; it does not imply physical feedback.
- Result codes: 0 none,1 armed,2 policy executed,3 blocked/late,4 cancelled. Source codes:0 unknown,1 manual/confirmed voice,2 schedule,3 conservation OFF/timer,4 SafetyKernel cutoff. A marks source4 by observing the actual periodic kernel transition, not by guessing from elapsed time.
- Review dialogs expire after 30 seconds or a controller boot change. Calendar/time edits, timezone or DST behavior need device testing; controller timing uses monotonic uptime once armed.
